# 지식 그래프 + 코드 분석 도구 통합 — 기대와 실측

> [English Version](10-knowledge-graph-and-tools-en.md)

Mickey는 두 개의 축으로 "세션이 쌓일수록 똑똑해지는" 구조를 만든다:

1. **개인화 지식 그래프** (`~/.kiro/mickey/domain/`) — 프로젝트를 넘어 재사용되는 도메인 지식
2. **코드 분석 도구 통합** (v9.2, §19) — Serena / Graphify / Kiro CLI 내장 `code`에 상세 분석 위임

이 문서는 각 축에 대해 **무엇을 기대했고, 실제로 어떤 결과가 나왔는지**를 실측 데이터와 사례로 정리한다. 잘된 것만 고르지 않았다 — 실패 사례가 오히려 설계를 바꾼 지점들이다.

---

## 1. 지식 그래프: 기대했던 효과

| # | 기대 | 근거 설계 |
|---|------|----------|
| E1 | 같은 판단/실수를 **다른 프로젝트에서 반복하지 않는다** | 세션 교훈 → Curator 분기 → 글로벌 승격 |
| E2 | 검색하지 않아도 **자연히 발견된다** (Passive) | INDEX 트리거 + GRAPH backlink + "언제" 힌트 |
| E3 | 세션 시작 비용 최소화 | 지식 지도(INDEX)만 로딩, 본체는 on-demand |
| E4 | 지식이 **자기 강화**된다 | 승격 루프 + 그래프 무결성 검증 |

## 2. 지식 그래프: 실측 결과

### 규모와 건전성 (2026-09-05, graph_audit.py 실측)

- **175 노드 / 515 엣지** (상위 그래프 148+488, cloud 하위 그래프 27+27), entry 파일 173개
- 무결성: **dangling 엣지 0, 경로 결손 0** — 승격 스크립트의 무결성 검증/자동 롤백이 유지
- 평균 차수 5.89 — 신규 지식이 고립되지 않고 기존 지식과 연결된 채 추가됨
- 최대 허브: `deploy-output-distrust` (차수 59) — "도구의 성공 출력을 불신하고 외부 신호로 교차 검증하라"가 전 도메인을 관통하는 중심 원칙이 됨
- 성장 속도: 2026-08-25 기준 131 노드 → 한 달여 만에 175 노드 (개발자 1인, 10여 개 프로젝트 병행)
- 활용도 baseline (5주 31세션 실측): **세션당 글로벌 지식 참조 2.45회**, Curator 호출 2.65회

### 긍정 사례

**사례 1 — cp949 3연작: 반복 실패의 점진적 봉합.**
Windows cp949 콘솔에서의 인코딩 실패가 형태를 바꿔 3번 재발했다: ① Python 스크립트 UnicodeEncodeError (M22) → ② 콘솔 한글 출력 잘림 (M39) → ③ PowerShell `>` 리다이렉트가 utf-8 출력을 mojibake로 파괴 (M48). 각 발현마다 프로젝트 규칙(adaptive #8 → #14 → #19)으로 잡혔고, 3회차에서 발현 지점 4곳의 카탈로그와 함께 글로벌 entry(`windows-cp949-artifact-ascii-defense`)로 승격됐다. 이후 어느 프로젝트든 "리다이렉트", "mojibake" 트리거만 스치면 이 지식이 발견된다. **같은 계열 실패의 재발 표면이 발현될 때마다 좁아지는 구조** — E1의 실증.

**사례 2 — Serena 잠복 사고의 진단 사슬: 지식이 진단을 가속.**
agent JSON에 숨어 있던 `--project` 하드코딩이 7주간 모든 세션의 Serena 활성 프로젝트를 조상 디렉토리로 오지정했다(하단 4절 참조). 진단 과정 자체가 그래프의 도움을 받았다: 이전 세션의 인계 가설("상대 경로 해석 문제")을 **프로세스 cmdline 실측**으로 기각하고 실제 원인(설정 계층 override)을 특정했는데, 이 접근은 `mechanism-level-cause-attribution`("실패 원인 기억은 메커니즘 수준으로 재검증 후 인용")과 `prompt-doc-vs-runtime-loading`("실효 설정은 프로세스 cmdline 실측으로 확정") — 모두 과거 다른 사고에서 승격된 지식 — 의 직접 적용이었다. 해결 결과는 다시 `tool-implicit-root-path-trap` entry와 §19.3 규약으로 그래프에 환류됐다.

**사례 3 — 검증된 패턴의 전 프로젝트 전파.**
`batch-confirm-autonomous-proceed`(짧은 응답을 일괄 채택으로 해석해 자율 진행)는 한 프로젝트에서 11회+ 적용 실패 0을 실측한 뒤 patterns/로 승격됐고, 이후 모든 프로젝트에서 확인 마찰을 줄이고 있다. `safe-batch-replace`(count 가드 일괄 치환)는 10세대에 걸쳐 재사용이 검증됐다.

**사례 4 — 프로토콜 진화의 출처 다양성.**
T1.5 프로토콜(extended-protocols.md)의 최근 9개 버전(v20~v28) 변경 이력의 출처가 전부 서로 다른 프로젝트다: 그래프 분석 프로젝트(예시 목록 오독 발견), 게임 QA 자동화(기호-맥락 병기), 모더나이즈 프로젝트(재실행 진단), Mickey 자체(멀티 세션 격리, Serena 규약). **그래프가 프로젝트 간 학습 전달 통로로 실제 동작**하고 있다는 증거다.

### 부정 사례 — 그리고 설계가 어떻게 바뀌었나

**사례 5 — "쌓기만 한 지식"의 활용도 0% (M20 포스트모템).**
v8.1에서 지식 구조를 만들고 76세션을 돌린 뒤 grep으로 실측하자 **글로벌 지식 활용이 0%**로 측정됐다. 원인은 저장이 아니라 발견 설계였다: "필요할 때 검색하라"(Active)는 지시가 실제로는 한 번도 실행되지 않았다. 이후 Passive 발견(INDEX 트리거 매칭 + backlink + "언제" 힌트)으로 재설계했고, baseline이 세션당 2.45회 참조로 회복됐다. 이 실패 자체가 `quantitative-usage-measurement`("0% = 설계 결함")와 `passive-over-active-retrieval`로 승격됐다. **지식을 쌓는 것과 지식이 쓰이는 것은 완전히 다른 문제다.**

**사례 6 — "세션 중 자동 호출" 2회 실패 → 강제 중단점.**
지식 큐레이션을 "AI가 적절한 시점에 알아서 호출"하도록 설계한 것이 두 번 연속 실패했다(호출이 일어나지 않음). LLM에게 시점 판단을 맡기는 설계는 작동하지 않는다 — 세션 종료 같은 자연스러운 강제 중단점에 배치해야 확실히 실행된다(`forced-breakpoint-execution`).

**사례 7 — 그래프는 저절로 건강해지지 않는다.**
"다음 Curator 호출 때 반영 예정"으로 인계된 orphan 노드 1건이 **2개월간 방치**된 것이 전면 감사에서 발견됐다(M44). 실행 주체가 없는 인계는 방치된다 — 이 실측이 `graph_audit.py`(무결성/정리 후보 자동 감사)의 상비 도구화와 baseline 동결로 이어졌다. 현재의 "dangling 0"은 도구+중단점이 유지하는 상태이지, 자연 상태가 아니다.

**사례 8 — 멀티 세션 동시 쓰기 → LLM에게서 쓰기 권한 회수.**
병렬 Mickey 세션들이 글로벌 그래프에 동시에 쓰면 충돌한다. 해결은 프롬프트 지시가 아니라 구조였다: Curator는 프로젝트 로컬 staging에만 쓰고, 글로벌 반영은 락을 잡는 결정론적 스크립트(`promote_knowledge.py`)만의 권한으로 이원화했다(`staged-promotion-write-isolation`). **"LLM이 판단, 코드가 강제"** 가 멀티 세션 안전의 핵심이다.

## 3. 코드 분석 도구 통합: 기대했던 효과

v9.2에서 외부 코드 분석 도구를 3-Tier로 통합했다 (Tier 1: Serena/Graphify, Tier 2: 사용자 지정, Tier 3: Kiro CLI 내장 `code` = baseline).

| # | 기대 | 근거 설계 |
|---|------|----------|
| T1 | Mickey 문서의 **상세 분석 부담 제거** | FILE-STRUCTURE를 first-step 지도로 축소, 상세는 도구 위임 |
| T2 | context window 절약 | 코드 관계를 문서에 박제하지 않고 on-demand 조회 |
| T3 | 정밀 분석 확보 | LSP(references/definition/diagnostics) + 심볼 검색 + 아키텍처 그래프 |
| T4 | "도구 없음" 케이스 제거 | 내장 `code`가 항상 존재하는 baseline |

## 4. 코드 분석 도구 통합: 실측 결과

### 긍정 사례

**사례 9 — 문서 다이어트가 실제로 유지비를 낮췄다.**
FILE-STRUCTURE.md가 "코드 관계 백과사전"에서 depth 2 트리 + 문서 위치 + 도구 감지 결과로 축소된 뒤, 노후화 주기가 길어지고 갱신 비용이 크게 줄었다. Brownfield 온보딩에서도 구조 분석 문서가 도구 참조 2~3줄(`structure-ref.md`)로 대체된다. 기대 T1/T2의 실증.

**사례 10 — 감지 규칙 자체가 실측으로 진화.**
한 벤치마크 프로젝트에서 로컬 마커(`.serena/`) 미감지를 "도구 부재"로 오판해 baseline으로 후퇴할 뻔한 사례가 나왔다 — 실제로는 MCP 도구 목록에 Serena가 노출되어 즉시 사용 가능했다. 이 갭이 §19.2 5항("마커 미감지 ≠ 도구 부재")으로 봉합됐다. 도구 통합 규약도 지식 그래프처럼 실패 실측으로 성장한다.

**사례 11 — 이 저장소 자체의 운영.**
Mickey 저장소는 Python 스크립트 30여 개 + 문서 300여 파일 규모인데, 심볼 탐색과 구조 파악을 Serena/내장 `code`(pyright LSP)에 위임하고 Mickey 문서는 지도만 유지한다. 이 문서를 만든 세션도 Serena `activate_project` → 실측 → 문서 갱신 흐름으로 진행됐다.

### 부정 사례 — 도구 통합의 비용

**사례 12 — Serena `--project` 하드코딩: 7주 잠복한 fail-wrong 사고.**
도구 통합 이후 최대 사고. agent JSON에 하드코딩된 `--project` 기동 인자가 글로벌 MCP 설정을 통째로 override하여, **한 달 반 동안 모든 세션의 Serena가 조상 디렉토리를 활성 프로젝트로 오지정**했다. 파일 쓰기가 엉뚱한 위치로 가서 타 프로젝트 세션 파일이 유실됐다. 조용히 잘못 동작하는 것(fail-wrong)은 에러를 내는 것(fail-closed)보다 훨씬 위험하다 — 해결은 기동 인자 폐지 + 세션 시작 시 `activate_project` 의무화 + 활성 확인 전 쓰기 금지(§19.3)였고, 멀티 세션 병렬 검증(프로세스 24개 cmdline 전수 + 활성화 로그 + 오배치 시그니처)으로 종결됐다. **교훈: 도구를 붙인다는 것은 설정 계층과 암묵 상태라는 새로운 실패 표면을 함께 붙이는 것이다.**

**사례 13 — 도구 경유 실행의 한계.**
Serena의 `execute_shell_command`는 timeout 240초로, 6분 이상 걸리는 Curator headless 실행을 감당하지 못한다(호출 측 절단 실측). 장주기 작업은 도구를 우회해 직접 실행 계층을 쓰도록 규약화했다. 도구의 강점 영역(심볼/구조 분석)과 한계 영역(장주기 실행)을 실측으로 구분해야 한다.

## 5. 종합: 기대 대비 결과

| 기대 | 판정 | 실측 근거 |
|------|------|----------|
| E1 반복 방지 | **유효** | cp949 3연작 봉합, T1.5 v20~v28 전부 타 프로젝트 발 |
| E2 Passive 발견 | **유효 (재설계 후)** | M20 활용도 0% → Passive 전환 → 세션당 2.45회 |
| E3 시작 비용 최소화 | 유효 | INDEX 지도 로딩 + on-demand 본체 (3-Tier 로딩) |
| E4 자기 강화 | **유효 (도구+중단점 조건부)** | 무결성 0/0 유지 — 단 graph_audit + 락 + 강제 중단점이 유지하는 상태 |
| T1/T2 문서 다이어트 | 유효 | FILE-STRUCTURE 축소, structure-ref 2~3줄 |
| T3 정밀 분석 | 유효 | Serena 심볼 + LSP diagnostics 일상 사용 |
| T4 baseline 확보 | 유효 | 내장 `code` 상시 + 마커 미감지 갭 봉합 |

관통하는 결론은 세 가지다.

1. **가장 큰 가치는 "지식 재사용"이 아니라 "실패의 구조적 봉합"이었다.** 같은 실패가 프로젝트 규칙 → 글로벌 entry → 코드(락/스크립트/규약)로 단계 상승하며, 재발 표면 자체가 물리적으로 줄어든다.
2. **자동은 없다.** 지식 활용도, 그래프 건전성, 도구 설정 — 전부 "알아서 되겠지"로 방치한 지점에서 실패가 실측됐고(0% 활용, orphan 2개월, 7주 잠복 사고), 실측 + 강제 중단점 + 도구화로만 회복됐다.
3. **LLM이 판단하고, 코드가 강제한다.** 승격 무결성은 스크립트가, 동시성은 락이, 호출 절차는 단일 진입점이 보장한다. 프롬프트 지시만으로 지켜지는 규약은 없었다.
